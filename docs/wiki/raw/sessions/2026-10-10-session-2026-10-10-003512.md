### Resend accepts inbound mail at a free Resend-managed `<id>.resend.app` subdomain (no domain of the user's own required), and received mail is retrievable over the ordinary API — `GET /emails/receiving`, up to 100 per page, paged with `after`/`before` — so a background fetcher can pull inbound mail by polling, with no webhook endpoint and no public URL.
Kind: fact
Evidence:
- source: https://resend.com/docs/dashboard/receiving/introduction.md — "Resend provides all the tools you need to receive emails (commonly called inbound) at [a verified domain](/docs/dashboard/domains/introduction), or at your account's Resend-managed `<id>.resend.app` subdomain."
- source: https://resend.com/docs/api-reference/emails/list-received-emails.md — "Retrieve a list of received emails for the authenticated user. … curl -X GET 'https://api.resend.com/emails/receiving'"
Verdict: reject_unsupported (grounded 0.55, derivable 0.19, importance 0.55, criticality 0.48)

### A received email fetched from Resend comes with two things the IMAP and Graph sources of this package do not provide: a signed download URL for the original raw message file (so the spool keeps a real `.eml`), and server-computed SPF/DKIM/DMARC verdicts that the sender cannot forge.
Kind: fact
Evidence:
- source: https://resend.com/docs/api-reference/emails/retrieve-received-email.md — "The SPF, DKIM, and DMARC results computed when the email was received. These come from the receiving mail server, not from the message headers, so the sender cannot forge them."
- source: https://resend.com/docs/api-reference/emails/retrieve-received-email.md — "Raw email content download information. Contains a signed URL to download the original email file including all attachments."
Verdict: reinforce (grounded 0.81, derivable 0.31, importance 0.57, criticality 0.51)

### Sending outbound mail to arbitrary recipients through Resend requires a domain verified in the user's account; the built-in `resend.dev` sender can only mail the account owner's own address, so any reply capability through Resend costs the user a domain they control.
Kind: fact
Evidence:
- source: https://resend.com/docs/knowledge-base/403-error-resend-dev-domain.md — "The `resend.dev` domain is only available for testing purposes and can only send emails to the email address associated with your Resend account."
- source: https://resend.com/docs/knowledge-base/how-do-I-create-an-email-address-or-sender-in-resend.md — "Once a domain is verified in your Resend account, you can send from any email address at that domain."
Verdict: review (grounded 0.75, derivable 0.19, importance 0.58, criticality 0.39)

### Resend's free plan allows 3 domains at 100 emails per day and 3,000 per month, and inbound mail counts against the same quota as outbound; its stated data retention on the free plan is 30 days, so a fetcher that stays offline longer than that cannot catch up on what it missed.
Kind: fact
Evidence:
- source: https://resend.com/pricing — "Free: 100 emails a day, 3 domains, Ticket support, 10,000 automation runs, 30-day data retention."
- source: https://resend.com/docs/api-reference/rate-limit.md — "Both sent and received emails count towards these quotas."
Verdict: reject_unsupported (grounded 0.54, derivable 0.16, importance 0.47, criticality 0.44)

### Resend's own agent-inbox product models agent replies as drafts: its `enabled_actions` list for an inbox offers `draft_reply` and no send action, and its agent guidance ranks a strict sender allowlist as the recommended first security level — a gate this package deliberately does not have (decision c1), so adopting that posture would reverse a decision rather than extend it.
Kind: fact
Evidence:
- source: https://resend.com/docs/api-reference/inboxes/get-agent.md — "Actions the agent is allowed to take. Each entry is one of `draft_reply`, `forward_thread`, `add_labels`, `assign_thread`, `mark_as_spam`, `archive_thread`, or `delete_thread`."
- source: https://resend.com/docs/openclaw-guide.md — "**Strict Allowlist**: Only allow emails from specific senders. **Recommended for most use cases**."
Verdict: review (grounded 0.79, derivable 0.20, importance 0.48, criticality 0.45)

### Threading an agent's reply through Resend is header work rather than an API feature — `In-Reply-To` carries the received `message_id`, with prior ids appended to `References` — and a send request can carry an `Idempotency-Key` (unique per request, expiring after 24 hours) so a retry after a crash cannot send twice.
Kind: fact
Evidence:
- source: https://resend.com/docs/dashboard/receiving/reply-to-emails.md — "If you want to reply to an email, add the `In-Reply-To` header set to the `message_id` of the received email."
- source: https://resend.com/docs/dashboard/receiving/reply-to-emails.md — "If you're replying multiple times within the same thread, make sure to also append the previous `message_id`s to the `References` header, separated by spaces."
- source: https://resend.com/docs/api-reference/emails/send-email — "Add an idempotency key to prevent duplicated emails. … Idempotency keys expire after **24 hours**"
Verdict: file (grounded 0.91, derivable 0.23, importance 0.62, criticality 0.35)
